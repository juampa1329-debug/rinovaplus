# Compatibilidad de las migraciones con SQL Server 2019

Actualización P1.2: el runtime comparte ahora un contrato positivo de perfil/destino, SQL 2019, compatibilidad y TLS; el catálogo verifica identidad antes de negocio y el workspace conserva marker/forma. [Implementación y límites offline](P1_2_CONTRACT.md). Las observaciones P1.1 inferiores sobre el runtime describen ese corte histórico; los **19 SQL y nueve runners no se editaron**. No quedan resueltos por ello sus guards/transacciones/drift ni se habilita ejecución institucional.

P1.1 · 24 de octubre de 2026. **No se identificó sintaxis posterior a SQL Server 2019 en los 19 archivos revisados. La ejecución institucional todavía no está lista:** los scripts y runners están condicionados a una copia local específica y hay diferencias de transacción, validación y reejecución. No se compiló SQL, consultó una base ni aplicó DDL/DML en este corte.

## Compatibilidad del lenguaje

| Elemento observado | Revisión para 2019 | Evidencia |
|---|---|---|
| `uniqueidentifier`, `nvarchar(max)`, `datetime2(7)`, `bit`, `decimal` | Tipos disponibles; no se usa JSON nativo ni VECTOR. Mantener Unicode, precisión y semántica UTC. | [Catálogo de columnas](SCHEMA_CATALOG.md). |
| `ISJSON(expr)` y `FOR JSON PATH` | Formas disponibles antes de 2019. Los CHECK usan validación de JSON textual; algunos verifican además objeto/array por su primer carácter. La validación tipada del contenido sigue en aplicación. | [001:34](../../../backend/migrations/001_local_crm.sql#L34), [018:28](../../../backend/migrations/018_campaigns.sql#L28); [ISJSON oficial](https://learn.microsoft.com/en-us/sql/t-sql/functions/isjson-transact-sql?view=sql-server-ver15). |
| `OPENJSON` y `STRING_SPLIT` | 006 los usa para derivar configuración existente. La base necesita compatibilidad suficiente; el guard de 001–009 exige ≥130. No cambiar el nivel automáticamente. | [006:38](../../../backend/migrations/006_crm_configuration.sql#L38), [001:7](../../../backend/migrations/001_local_crm.sql#L7); [OPENJSON oficial](https://learn.microsoft.com/en-us/sql/t-sql/functions/openjson-transact-sql?view=sql-server-ver15). |
| `STRING_AGG` | Disponible desde SQL Server 2017. 006 convierte la expresión a `nvarchar(max)` y evita el límite de la variante de longitud fija. | [006:37](../../../backend/migrations/006_crm_configuration.sql#L37); [STRING_AGG oficial](https://learn.microsoft.com/en-us/sql/t-sql/functions/string-agg-transact-sql?view=sql-server-ver15). |
| Índices filtrados, claves compuestas, `IDENTITY`, `CHECK`, FK | Sintaxis anterior a 2019. El inventario distingue índices explícitos de restricciones que generan índices; la aceptabilidad de datos existentes se comprueba después en una copia. | [012:20](../../../backend/migrations/012_channels_identity_collation.sql#L20), [019:34](../../../backend/migrations/019_admissions_agents.sql#L34). |
| `THROW`, `TRY/CATCH`, `XACT_ABORT`, `sp_getapplock`, SHA2, metadatos y propiedades extendidas | No requieren una versión posterior. Los permisos, el propietario de la transacción, duración de locks y consistencia de metadatos son condiciones operativas pendientes. | [001:2](../../../backend/migrations/001_local_crm.sql#L2), [001:12](../../../backend/migrations/001_local_crm.sql#L12), [020:10](../../../backend/migrations/020_agent_execution.sql#L10). |
| Funciones posteriores | No se encontraron `DATETRUNC`, `DATE_BUCKET`, `GENERATE_SERIES`, constructores JSON nuevos, `ISJSON` con segundo argumento o `STRING_SPLIT` con ordinal. El detector acotado no es un compilador ni una prueba exhaustiva de sintaxis. | [inventory.json](inventory.json), campo `post_2019_candidates`. El segundo argumento de ISJSON fue introducido en 2022, según su documentación oficial. |

La exigencia de compatibilidad ≥130 del sistema no se deriva sólo de `ISJSON`: `OPENJSON` y los guards explícitos importan. La versión del motor, la edición y el nivel de compatibilidad de una base son datos distintos. Sólo la versión **2019** está confirmada por el propietario.

## Bloqueos y riesgos concretos

| ID | Prioridad | Hecho observado | Acción posterior |
|---|---|---|---|
| SQL-01 | Alta | Los 19 scripts requieren `DBSIIE`/`SQLEXPRESS`; configuración y `verify_target` añaden host/máquina/certificado/contrato locales. Esto no es un requisito del motor 2019. | P1.2: contrato positivo por entorno y destino autorizado, preservando TLS, marca de esquema y verificación. No borrar guards para conseguir conexión. |
| SQL-02 | Alta | 011–017 comparan `InstanceName` sin normalizar NULL. Si la base coincide y el nombre de instancia es NULL, el `OR` puede dar UNKNOWN y el IF no lanza error. 001–009 y 018–020 sí usan `ISNULL`. | Definir comprobación segura para el camino institucional. Mantener las migraciones históricas; decidir la evolución explícita en P1.2/P1.3. |
| SQL-03 | Alta | Los runners pasan primero por `verify_target`, que compara una tupla exacta y rechaza NULL. El defecto SQL-02 no demuestra que esos runners omitan la protección. SQL ejecutado directamente y runner son dos fronteras diferentes. | Probar ambas fronteras negativamente antes de autorizar ejecución. No extrapolar el riesgo a un bypass productivo demostrado. |
| SQL-04 | Alta | 001–009 rechazan una transacción ya abierta y gestionan la suya. 011–017 se apoyan en el caller para atomicidad completa; `XACT_ABORT` solo no agrupa todos los cambios. 018–020 exigen transacción del caller. | Un futuro runner debe conocer el propietario transaccional de cada unidad. No envolver todos los archivos en una única transacción ni ejecutarlos todos en autocommit. |
| SQL-05 | Media | 001–009 guardan contrato/huella y recomponen forma. Varios scripts posteriores aceptan un marcador sin comprobar toda la estructura; 018–020 rechazan determinados estados existentes y sus runners añaden controles propios. | Diseñar historial y preflight de forma por unidad. Marcador, idempotencia y detección de drift no son equivalentes. |
| SQL-06 | Media | 014 localiza un CHECK que contiene Provider y lo reemplaza; no añade un marcador de versión específico y no es un no-op al repetir. 012 cambia collations y recrea claves mediante SQL dinámico. | Revisar estado previo, permisos, dependencias y plan de fallo antes del ensayo; no representar estos scripts como sólo creación de tablas. |
| SQL-07 | Media | No hay runner 001–009 versionado en `backend/tools`; los nueve runners presentes cubren diez archivos posteriores. Ninguno divide batches GO; estos 19 archivos no contienen separadores GO. | Conservar la distinción ejecución manual histórica/runner. No emitir una receta de aplicación automática a partir del orden de nombres. |
| SQL-08 | Media | 009 referencia `crm_inbox.Task`: necesita 003 por FK aunque el guard de contrato no detalle toda esa dependencia. Otras dependencias por FK están en el inventario y el grafo. | Preflight de dependencias explícito; no confiar sólo en el marker que comprueba cada archivo. |
| SQL-09 | Media | 006 inserta configuración derivada de datos CRM; 013 crea conexión deshabilitada y su runner puede importar ajustes no secretos; 017 crea política IA deshabilitada; 018 crea Policy con evaluación periódica interna habilitada. | No llamar a todas las migraciones «sin datos» o «todo apagado». Estos cambios no son semillas demo ni habilitan por sí solos envíos. |
| SQL-10 | Media | No hay scripts DOWN. El rollback de una transacción fallida no revierte una migración ya confirmada. | P1.3: recuperación ensayada, compatibilidad de aplicación y reversión por unidad; no borrar datos para volver atrás. |
| SQL-11 | Media | No hay DDL/DML académico explícito en estos archivos, pero la base puede tener triggers de auditoría DDL. La autorización histórica local de sus INSERT no se extiende automáticamente a otro entorno. | Revisar efectos del destino real en la etapa autorizada, conservando la auditoría. No deshabilitarla para hacer pasar una comparación. |

`SERVERPROPERTY('InstanceName')` devuelve NULL para la instancia predeterminada, según [Microsoft](https://learn.microsoft.com/en-us/sql/t-sql/functions/serverproperty-transact-sql?view=sql-server-ver15). Si SQL también se instala en Linux, Microsoft documenta una instancia predeterminada por host y conexión por puerto; no corresponde exigir allí una instancia nombrada Windows. **La aplicación Linux/Docker no obliga a mover el SQL existente a Linux.** [Características de SQL Server 2019 en Linux](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-editions-and-components-2019?view=sql-server-ver15).

## Criterio de entrada para P1.2

Primero seleccionar la unidad y definir el contrato de entorno: base esperada, identidad del servidor, versión 15.x, edición/compatibilidad leídas cuando se autorice esa lectura, marker/forma del CRM, DNS/TCP, certificado y permisos mínimos. Distinguir desarrollo/copia local de institución; no reutilizar `local_sql_copy` como modo productivo sin revisar su significado.

El primer cambio ejecutable propuesto es acotar ese contrato en `config.py`, `sql_workspace.py` y el lector de catálogo, con casos positivos/negativos aislados y sin aplicación de DDL. La secuencia de nuevas migraciones e historial pertenece a P1.3. Toda prueba SQL conectada se hará después en la copia/entorno identificado, preservando respaldo, auditoría y política de cambios.

## Límite de esta aceptación

P1.1 puede cerrar como **inventario y compatibilidad estática revisados**. No acredita que las 68 tablas existan en la base institucional ni que permisos, datos, certificados, edición, constraints o concurrencia pasen en ella. El catálogo conserva 596 columnas CREATE y, por separado, la columna RunId añadida por ALTER en 018; también conserva cambios de collation y DDL dinámico sin fingir una reconstrucción final ejecutada.
